# 旅行规划 Agent 学习项目设计

## 项目目标

通过逐阶段实现一个可运行、可观察、可测试的旅行规划 Agent，理解 Agent Runtime 的具体控制流，并为后续阅读 Hermes 等成熟 Agent 项目建立自己的实现参照。项目以工程实践为主，也把 Git 基础练习嵌入每次小步交付。

项目不以“尽快堆出功能”为目标。每个阶段都要让学习者能追踪一条真实数据流、运行行为检查，并用自己的话解释关键状态与设计取舍。AI 负责拆任务、解释陌生概念、审阅实现和设计验收；学习者负责阅读、运行、解释，并承担主要实现练习。

## 设计原则

- **先手写核心，再映射框架**：先用普通 Python 实现最小 Runtime；不让 LangGraph 等框架隐藏控制流。后续再建立机制映射。
- **先确定性，后真实模型**：Fake Model 先验证 Agent Loop 和工具往返；真实模型只替换模型适配层，不接管 Runtime 的权限和状态控制。
- **每一步都可观察**：记录输入消息、模型请求/响应、状态变化、工具调用和最终结果；初期使用终端轨迹，不先建设复杂观测平台。
- **分清相邻概念**：RAG 用于查找外部资料，Memory 用于保存和回忆用户/Agent 信息；运行时 Harness 和评测 Harness 分开。
- **先实现最小有用机制**：先关键词检索、SQLite、本地工具和单进程队列；向量检索、分布式队列等按学习目标后置。
- **不冒用真实业务能力**：天气、酒店和景点能力优先使用固定数据或 Fake Tool。真实模型与外部服务只有在用户明确选择并配置后才接入。
- **先覆盖 Harness 主干，再补生产扩展**：项目会实现 Agent Harness 的核心控制面；对分布式调度、复杂沙箱和供应商级观测只做边界理解，不为“覆盖名词”而堆砌系统。
- **Git 小步且可解释**：每个阶段练习检查状态与差异、选择性暂存、提交、分支、合并和历史回看；不自动提交或推送。

## 贯穿案例

用户说：“我想下周去上海玩三天，预算 2000 元，喜欢历史景点。” Agent 最终给出一份有依据、能解释预算取舍的计划。

这个案例逐步引入：用户消息和模型回复、工具调用与工具结果、旅行资料检索、偏好记忆、外部能力协议、多工具并发和轨迹评测。前期所有结果均可由固定假数据重复验证，避免网络、API 费用或模型随机性掩盖控制流。

## 系统边界与演进架构

初始阶段只包含 CLI、Agent、Model、Message 和结构化终端轨迹。能力逐步增长，但始终保持这条主要控制流：

```text
CLI 输入
  -> Agent Runtime 构造本轮请求
  -> Model 返回文本或动作建议
  -> Runtime 校验并决定继续、执行能力或结束
  -> 工具/检索/记忆结果成为新观察
  -> Runtime 再次请求模型或返回最终结果
```

后续目录按实际复杂度逐步形成，不在第一天预建空模块：

```text
app/
  domain.py       消息、动作、事件、运行结果等核心数据
  model.py        Fake Model 与真实模型适配
  runtime.py      Agent 循环、停止条件和运行时控制
  tools.py        工具契约、注册与分发
  rag.py          旅行资料切分和检索
  memory.py       用户偏好等记忆的读写与召回
  mcp_client.py   外部 MCP 能力发现与调用
  queue.py        工具任务的顺序、并行和取消
  harness.py      独立的运行时控制和评测回归能力
tests/
docs/
```

SQLite、CLI 持久化和服务 API 只在对应阶段加入；早期课程可用脚本与内存状态降低干扰。

## 分阶段路线与成功标准

| 阶段 | 能力增量 | 核心理解与验收 |
| --- | --- | --- |
| 0. 项目与 Git 起步 | 独立项目骨架、CLI 输入、消息结构、Fake Model、可读轨迹；初始化项目自己的 Git 仓库前先核实仓库边界 | 能解释工作区、暂存区、提交之间的差异；运行一次输入到普通文本回答的完整轨迹 |
| 1. 最小 Agent Loop | Fake Model 先返回文本，再按预设脚本请求一次工具、收到结果后总结 | 能沿 `messages -> model -> action -> observation -> model -> final` 手工追踪数据与停止条件 |
| 2. 工具系统 | 工具契约、名称、参数 schema、注册表、分发器、错误结果 | 错误工具名/非法参数不应调用工具；工具异常能形成可观察结果并按策略继续或停止 |
| 3. 真实模型适配 | `ModelProvider` 接口、Fake Model 和一个 OpenAI-compatible Provider | 能说清 Runtime 与供应商 API 的边界；未配置密钥时 Fake Model 与测试仍能运行 |
| 4. 会话持久化 | SQLite 保存 sessions、messages 和工具交互记录 | 能中断并恢复会话；能区分持久化历史与单次运行状态 |
| 5. Prompt 与上下文 | system prompt、历史、工具定义、实际发送请求的组装 | 能对比“数据库中保存的内容”和“本次真正发给模型的内容” |
| 6. RAG | 旅行文档切分、关键词检索、证据引用；向量检索作为后续增强 | 用固定文档证明命中与未命中行为；回答能区分证据和猜测 |
| 7. Memory | 用户偏好写入、搜索、召回、进入上下文 | 能区分 RAG 证据与用户记忆；能检查错误或过期偏好导致的后果 |
| 9. Agent Harness 核心 | 运行时 Harness：超时、最大迭代、重试、中断、权限、资源清理、状态、checkpoint/replay、人工确认、成本/工具预算；评测 Harness：任务、轨迹、工具正确性、答案判定、回归集、故障注入 | 能指出两类 Harness 各自的责任；一次中断恢复、一次故障注入和一次离线回归可重复验证 |
| 10. 多 Agent 编排 | supervisor/worker、角色边界、handoff、独立上下文、共享状态最小化、并行 worker、失败传播和取消 | 能判断何时不该拆 Agent；能说明 handoff 与普通工具调用的区别，并验证必需 worker 失败不会生成伪造答案 |
| 11. MCP | 极小本地 MCP Server，通过 Client 发现并调用天气/笔记能力，再接回工具注册层 | 能对照本地函数调用与协议调用，解释 Host/Client/Server、能力发现和信任边界 |
| 12. 扩展机制 | 选择性实现 Skill、Plugin hook、Delegation 适配；多 Agent 的跨进程协议只做边界映射 | 能说明每种扩展解决的问题与引入的复杂度；不为覆盖名词而实现不必要框架 |
| 13. 工程整合 | 按需加入 FastAPI、数据库迁移/事件流、服务级测试；将手写机制映射到 LangGraph | 能从入口追踪一次服务请求；能解释何时保留自建机制、何时采用框架 |
| 14. 成熟项目对照 | 回到 Hermes/EvoAgent Harness，选一条具体 CLI 请求、工具调用或恢复链与本项目逐段比较 | 能按调用链定位入口、Runtime、工具执行、Session/Memory、Harness 和多 Agent 边界，而不是逐文件通读 |

阶段不是必须一次性连续完成。你可以比预计速度更快推进，但每阶段的口述、运行证据和失败路径检查不能跳过；如果基础缺口暴露，就只补当前阻塞点。阶段 0 和 1 优先于下周二（2026-10-20）实习开始前完成；在时间允许时继续阶段 2，不以赶进度牺牲理解和测试质量。

## Harness 覆盖范围

这里的“覆盖 Harness”指覆盖 Agent 执行与评测所需的核心控制面，不声称复刻某个成熟项目的全部生产组件。

本项目主线会实际实现或验证：

- 运行边界：最大步数、超时、取消、中断、重试、工具权限和资源清理；
- 状态与恢复：运行状态、事件记录、checkpoint、失败后 replay，以及人工确认后的继续执行；
- 资源约束：模型调用、工具调用、总耗时和成本/次数预算；
- 结果可信度：工具结果与最终答案一致性、失败传播和安全停止；
- 评测闭环：固定任务集、轨迹记录、工具/答案断言、故障注入、回归比较；
- 调试基础：结构化事件、trace/span 关联、脱敏和确定性 Fake Model。

只做概念映射或后置讨论的内容：分布式调度、多进程隔离、容器沙箱、复杂资源配额、生产级分布式 tracing、跨系统 A2A 协议和供应商专属 Harness。它们会在成熟项目对照阶段标出与本项目的边界，不伪装成已经实现。

## 单阶段实施与教学循环

```text
说清本阶段解决的问题和主案例
  -> 画输入、状态、输出的数据流
  -> 写行为测试/验收断言
  -> 学习者阅读并完成最小实现
  -> 运行测试并观察事件轨迹
  -> 对照一种常见错误实现
  -> 学习者口述机制并完成小改动
  -> 检查 Git diff，学习者决定是否提交
```

新术语和 API 在要求使用前解释；代码按逻辑片段讲解，先追踪一轮真实数据，再讲抽象。每个阶段有明确输入、预期输出、失败边界和测试命令，不把“程序跑起来”当成理解通过。

## Git 与 GitHub 学习边界

- Git 练习使用独立旅行 Agent 项目仓库，避免把 Agent 学习区或现有项目的历史混在一起。
- 在确认 `E:\agent_learn\.git` 实际状态和目标目录边界前，不运行 `git init`、不修复/删除该目录、不改写 Git 历史。项目仓库位置须由 Git 检查结果确定。
- 起步掌握 `status`、`diff`、`add`、`restore --staged`、`commit`、`log`、分支切换、合并冲突和冲突解决。
- 每次提交前先由学习者检查变更摘要与 diff；AI 不自动 commit 或 push。
- GitHub 阶段再学习 remote、clone、fetch、pull、push、Pull Request、review 和 CI。只有用户决定远程仓库和可见范围后，才进行创建或推送等远程写操作。
- 不把“Git 命令背熟”当作目标；验收以能回答当前改动在哪里、哪些内容会提交、如何检查历史和如何协作合并为准。

## 非目标

- 第一阶段不使用 LangGraph/LangChain，不先接真实天气、地图或机票 API。
- 不把 MCP、Skill、Plugin、多 Agent 全部塞入最小版本。
- 不在没有工作负载和验收需求时引入向量数据库、分布式队列、Kubernetes 或云部署。
- 不直接改写 Hermes 源码；本项目先作为理解参照。
- 不把教程复制粘贴或让 AI 一次性生成完整工程作为主要学习方式。

## 验收原则

每阶段完成需同时满足：

1. 学习者用自己的话解释该阶段的核心机制、状态变化和一项重要边界。
2. 学习者运行行为测试/练习，输出与预期一致；失败路径也有对应检查。
3. 学习者能检查本阶段 Git 差异，并说明暂存内容和提交内容的范围。

在以上证据齐备前，阶段保持“学习中”或“待补强”，不标记“已掌握”。
